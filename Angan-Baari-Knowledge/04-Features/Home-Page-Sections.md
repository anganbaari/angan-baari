# Home Page Sections

`templates/index.html`'s product grid is a **hybrid**: some category
sections are hand-written, the rest are generated from the database, and
both kinds share one JS filtering system — they are not two separate
grids stacked on a page.

## Hand-written vs. database-driven

- **Hand-written, in the template directly**: Fruits (फलफूल), Honey
  (मह), Pickles (अचार), Vegetables (तरकारी).
- **Database-driven**: every other top-level `Category` (`parent=None`)
  that has at least one available product, generated by `home()`
  (`shop/views.py`) and looped into the template via
  `other_category_sections`.

```python
HOME_EXCLUDED_CATEGORIES = ['फलफूल', 'मह', 'अचार', 'तरकारी']
HOME_HIDDEN_CATEGORIES = []
```

`HOME_EXCLUDED_CATEGORIES` is "already covered by the hand-written
sections above, never duplicate" — matched against the real stored
Nepali `Category.name` strings, not the English labels used in
conversation. `HOME_HIDDEN_CATEGORIES` is a separate lever for hiding a
category from the home page later (e.g. while still being set up)
without touching the exclusion list, which specifically means "already
elsewhere on this page." Both live in `shop/views.py`, right above
`home()`.

## Why database-driven sections join the SAME grid

The key discovery made while building this: `static/script.js`'s
shop-tab/shop-card filtering is **one shared, page-wide system**, not
scoped per section. A tab click filters every `.shop-card` on the page by
its `data-cat` attribute; there's no per-section instance of this logic.
This meant a new category section generated from the database could not
be a visually separate block — it had to emit a new tab
(`data-cat="cat-<id>"`) and cards using the exact same markup/classes as
the hand-written ones, joining the one grid instead of forming its own.
Building a second, parallel filtering system for "the database-driven
part only" was considered and rejected as needless duplication once this
was understood.

Only "Fruits" starts active (not `hidden`); every other tab/card,
hand-written or database-driven, starts `hidden` until its tab is
clicked — same convention either way.

## Card content

Every card — hand-written or database-driven — shows: image, category
(icon + name), product name, and **one punchline line**:

```django
{% if product.tagline %}
<p class="shop-punchline">{{ product.tagline }}</p>
{% elif product.description %}
<p class="shop-punchline">{{ product.description|first_sentence|truncatechars:90 }}</p>
{% endif %}
```

- `Product.tagline` — a new `CharField` (migration
  `0050_product_tagline`), editable in admin, meant to be a short,
  deliberately-written line ("Sun-ripened, tree-fresh mangoes" rather
  than a trimmed product description).
- `first_sentence` (`shop/templatetags/storefront_tags.py`) — regex
  `[^.!?]*[.!?]`, i.e. up to and including the first `.`/`!`/`?`. Used as
  the fallback when `tagline` is blank, chained with Django's own
  `truncatechars:90` since no single built-in filter does both "first
  sentence" and "cap the length" at once.

**No card shows a price at all** — this was a deliberate replacement,
not an oversight: the original hand-written cards showed a price, and
every card (including database-driven ones, and regardless of pricing
mode — `fixed_quantity`, `variable_weight`, or `fixed_weight`/animals)
now shows the punchline instead. There's no price-vs-punchline split by
product type; it's punchline-only everywhere on this page.
