# Storefront and Vercel

The public shop front-end is a **separate Next.js project**, not in this
repo, deployed on Vercel at `https://angan-baari-shop.vercel.app`. It is
a genuinely separate hosted system with no other way to reach this
Django project's database — the same reasoning that makes ABMS ↔ Django
a legitimate REST API boundary (see [[ABMS-Integration]]) applies here
too. See [[REST-API]] for how the two boundaries compare.

This doc covers the mechanics: env vars, CORS, auth, and exactly which
Django page links switch to Vercel and which never do. For the
`/api/v1/` endpoint list itself, see `CLAUDE.md`'s "REST API (v1)"
section — this doc doesn't duplicate that list.

## Env vars

| Setting | Default | Purpose |
|---|---|---|
| `API_V1_CORS_ALLOWED_ORIGINS` | `http://localhost:3000,https://angan-baari-shop.vercel.app` | Comma-separated list `ApiV1CorsMiddleware` (`api/middleware.py`) allows to call `/api/v1/` cross-origin |
| `FRONTEND_BASE_URL` | `https://angan-baari-shop.vercel.app` | Single URL used for places that can only point at one destination (e.g. password-reset-confirm links the API emails) |
| `STOREFRONT_URL` | `` (empty) | Drives `{% storefront_link %}` — see below. Empty means "behave exactly as if Vercel didn't exist" |

All three are read via `os.getenv(...)` in `farmsite/settings.py`, no
trailing slash on any of them, by project convention.

## CORS and auth, by endpoint group

`ApiV1CorsMiddleware` is a narrow CORS layer scoped to `/api/v1/` only —
deliberately separate from the ABMS bridge's own `CORS_ALLOWED_ORIGINS`
(`corsheaders`), which stays scoped to `/api/inventory/movements/`. See
that middleware's own docstring for why it has to run before
`corsheaders.middleware.CorsMiddleware` in `MIDDLEWARE`.

Authentication is set **per view**, not globally — three different
shapes exist under `/api/v1/`:

1. **Public, no auth** (`authentication_classes = []`,
   `permission_classes = [AllowAny]`) — `products/`, `products/<id>/`,
   `products/by-slug/<slug>/`, `categories/`, `orders/` (create, guest
   checkout), `orders/<id>/` (status lookup, or full detail with
   `?token=`), `orders/<id>/cancel/`, `orders/<id>/reorder/`,
   `auth/signup/`, `auth/login/`, `auth/password-reset/`,
   `auth/password-reset-confirm/`.
2. **Token-authed, storefront's own logged-in calls**
   (`TokenAuthentication` + `IsAuthenticated`) — `auth/logout/`,
   `profile/`, `profile/orders/`, `profile/change-password/`,
   `wishlist/*`, `coupons/`. Token auth never goes through Django's
   session/CSRF machinery, so there's no CSRF header to send here —
   unlike the POS gotcha below.
3. **Session-authed, staff-only** (`SessionAuthentication` +
   `IsStaffUser` or `IsOwnerOrManager`) — every `pos/*` and `reports/*`
   endpoint, plus `inventory/movements/` and `costs/`. These are never
   reachable from Vercel's origin in practice (no staff login there),
   but the auth class is what actually enforces that, not the origin.
   `SessionAuthentication` *does* its own CSRF check independent of
   Django's middleware — `templates/pos.html`'s JS sends an explicit
   `X-CSRFToken` header on every call for exactly this reason.

## The links-only switch (Phase 1 — no redirects)

`shop/templatetags/storefront_tags.py`'s `{% storefront_link %}` tag is
the entire mechanism. It takes a `kind` (and sometimes an `arg`) and
returns either the existing Django URL (when `STOREFRONT_URL` is empty)
or the equivalent Vercel path (when it's set):

```python
_SIMPLE_LINKS = {
    'shop': ('shop', '/'),
    'cart': ('cart', '/cart'),
    'checkout': ('checkout', '/checkout'),
    'login': ('login', '/login'),
    'signup': ('signup', '/signup'),
    'profile': ('profile', '/profile'),
}
```

Plus two parameterised kinds: `'category'` (`?cat=<id>` on either side)
and `'product'` (`/product/<slug>` on Vercel,
`product_detail` by slug on Django).

**Used in 8 templates**: `index.html`, `shop.html`, `cart.html`,
`checkout.html`, `product_detail.html`, `auth/login.html`,
`auth/signup.html`, `auth/profile.html`.

**This is links only — no redirects, no server-side routing change.**
Visiting the Django URL directly still renders the Django page exactly
as before; only the `<a href>` values generated by the tag change. This
was a deliberate scope boundary for Phase 1, not a limitation to work
around.

### What stays on Django regardless of `STOREFRONT_URL`

The tag's own docstring is explicit about this, and it's enforced simply
by these templates never calling `{% storefront_link %}` for these
routes — there's no bypass to accidentally trigger:

- **Home page / logo** — the home page (`index.html`) is itself a
  Django-rendered page (see [[Home-Page-Sections]]); only the *links
  inside* it switch.
- **POS** (`/pos/`) — server-side staff login, never meant to be hosted
  anywhere but Django. See [[Architecture-Decisions]].
- **Admin** (`/admin/`) and the **Reports dashboard** (`/dashboard/`) —
  staff/owner-only, no storefront equivalent, ever.
- **`/cancel/<token>/`** — the order-cancel link emailed to customers
  (`shop/emails.py`). Still points at the PythonAnywhere domain even
  though emails are otherwise unrelated to this switch — Vercel has no
  route that could handle a bare cancel token.
- **The legacy password-reset flow** (`shop/auth_views.py`,
  `/account/reset-password/<token>/`) — kept running in parallel with
  the newer API-based flow Vercel actually calls
  (`POST /api/v1/auth/password-reset/` +
  `/api/v1/auth/password-reset-confirm/`). Two systems exist on purpose;
  don't assume there's only one when touching password reset.

## Deferred / known gaps

- **Offers now exist on both sides:** the public `GET /api/v1/offers/`
  feeds Vercel's own `/offers` page, and `{% storefront_link 'offers' %}`
  switches the Django nav links to it when `STOREFRONT_URL` is set (the
  Django `templates/offers.html` stays reachable at its own URL).
  `pos/offers/` is still the separate staff-only POS endpoint. See
  [[Offers-and-Cart-Quote]].
- **Coupons are not applied by the Vercel cart** — `GET /api/v1/coupons/`
  is shown read-only (profile, offers page).
- **Two password-reset systems**, as above — a future cleanup candidate,
  not urgent while both still work.
- **Order/cancel emails still hard-code the PythonAnywhere domain**
  (`shop/emails.py`'s `cancel_link`, admin links) rather than
  `FRONTEND_BASE_URL` — because the destination (`/cancel/<token>/`,
  Django admin) genuinely only exists on Django, this isn't inconsistent
  with the switch above so much as a reminder that "point emails at
  Vercel" was never the goal for routes Vercel doesn't have.
