# POS

- **Auth:** server-side staff login (`@staff_member_required`), **not a token**. Deliberate — avoids the token-exposure/CORS problem entirely, since unlike ABMS the POS has no reason to be hosted separately.
- **Frontend:** vanilla JS served by Django (`templates/pos.html`) — not React, not separately hosted. See [[Architecture-Decisions]] for why this isn't a gap to "fix."
- **Idempotency:** `POSSale.client_sale_id` — a UUID generated client-side before the sale is sent. A double-tap, a retried request, or a queued offline sale being resynced all return the original result instead of creating a duplicate sale.
- **Inventory writes:** POS calls `create_inventory_movements_from_snapshot()` in `strict=True` mode — re-raises on failure, calls `full_clean()`, expected to be wrapped in `transaction.atomic()` so a failed line rolls back the whole sale. Contrast with website checkout's `strict=False`. Full rationale in [[Inventory-Rules]].
- **Coupons (Phase C):** reuses the website's `Coupon` model — no parallel POS-only discount system. `resolve_pos_coupon(code, subtotal)` in `shop/views.py` is the single implementation of the rules (is_live, min_order_amount, calculate_discount), used both by the live preview (`POST /api/v1/pos/coupon/validate/`, no side effects) and by `create_pos_sale()` itself, which re-validates from scratch and is the only place a coupon is actually consumed (`used_count` incremented there, inside the same atomic transaction as the sale). An invalid/expired/no-longer-qualifying code is a **hard error** at sale creation — unlike the website checkout, which just shows an error banner and proceeds at full price. The discount comes off the pre-tax subtotal, then VAT (when enabled) is recomputed on the smaller taxable share, split in the same proportion the undiscounted cart had. `Offer`-style automatic per-product/category discounts are NOT wired into the POS — website-only for now, would need per-line price overrides in the product grid.

The `django.ce.exceptions` import typo (previously broke `full_clean()` for every POS sale) has been fixed and confirmed in the current codebase — no longer a live bug.
